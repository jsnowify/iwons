## Original findings (historical; addressed above)

1. **P2 - Streak and freeze actions retain yesterday's date after midnight.** `src/components/learning-progress.tsx:17` initializes `today` once in an empty-dependency effect. Keeping the progress page open overnight, returning from a sleeping tab, or recording new successful work after midnight updates learning state but never refreshes today. The streak display and freeze onClick (`:26`) keep calculating against the old day, potentially offering the wrong missed-day freeze and calendar-week allocation. Refresh the local date on day rollover and page visibility/focus, and derive the click's date from the current clock rather than the mounted value. The initial empty date avoids a server/client date mismatch, but does not handle ongoing date changes.

2. **P2 - Consecutive freezes can bridge two missed days across a week boundary.** `src/lib/foundations/learning-rewards.ts:24-25` tests prior coverage rather than prior successful activity. Example: last success Saturday 2026-10-10; on Monday 12 use a freeze for Sunday 11. On Tuesday 13, Monday 12 is offered because Sunday is now in covered and Monday belongs to a new calendar week. No success occurred Sunday or Monday, yet two consecutive missing days are bridged. This conflicts with the documented single-day bridge and the test name promising not to bridge multiple missing days. Require the day before the missed day to be active rather than merely frozen (or explicitly decide/document that consecutive cross-week freeze bridges are allowed). The existing multiple-gap test contains no already-frozen day, so it misses this case.

3. **P3 - Historical local-day rewards are recalculated in the current timezone.** `learning-rewards.ts:4-11` derives every event's local date using the environment's current timezone. Changing timezone can merge two originally separate credited days or split a previously same-day pair, changing accumulated XP without new answers. Streak history is similarly regrouped, whereas freeze strings remain pinned to their previously stored dates. If historical reward stability while travelling is expected, capture the event's local-day key (with a compatible fallback for older backups). If current-timezone regrouping is intended, document that behavior.

4. **P3 - Freeze validation checks calendar shape, not allocation constraints.** `src/lib/foundations/learning-state.ts:79-81` rejects impossible dates but permits duplicate days, multiple freezes in the same calendar week, future days and adjacent frozen days. UI normally prevents same-week reuse, so this is an import/data-integrity gap rather than a normal rerating exploit. Decide whether backups may faithfully retain irregular historical allocations or must satisfy the weekly rule; if enforcing it, add validation with an explicit migration/compatibility policy. Existing valid empty/date-string freeze records remain compatible.

5. **P3 - Reward text contains literal question-mark punctuation.** `src/components/learning-progress.tsx:26` contains `module?s lessons` and a ` ? ` separator between module title and track. Replace these with ordinary apostrophe/separator text. This is cosmetic but visible in the rewards explanation and stamp list.

## Confirmed source properties

- Recall XP uses a Set of card key plus local day over correct events. Repeated correct ratings of the same card on one day produce one 5-XP credit; failures produce none. The card key includes track. Correct recall rated Again still receives successful-retrieval credit, consistent with rewarding correctness rather than difficulty selection.
- Exercise XP is derived from solved booleans, yielding full first-track plus quarter additional-track credit. Repeated attempts cannot multiply it. Module XP is derived from the unique module/track stamp list, not accumulated click events. No duration, session count, or unsuccessful-attempt count adds XP.
- Streak active days come only from correct attempts/recalls. Quiet sessions, elapsed time and failures do not count. A correct Modify/ worked-example check also counts as successful practice under current event representation; UI wording “solves and recalls” is somewhat broader in effect than independent solves alone.
- UTC-noon calendar stepping avoids DST-length assumptions; weekStart uses Monday. Freeze availability correctly uses the week of yesterday/the missed day, including month boundaries. A missing today preserves yesterday's streak; two uncovered past days break it. The consecutive-frozen-day exception is finding 2.
- Generated reward index contains nine pilot exercise IDs with expected 5/20 XP values and one cp1-m1 exercise list. The generator includes ready modules and removes stale owned public assets. It introduces no hidden test packs or solutions into the reward index.
- Learning state remains in existing versioned storage/backup paths; new rewards are derived from existing events. Freeze strings already exist in that schema, so valid historical backups do not require new fields. Stricter rejection of impossible freeze strings is reasonable; it intentionally rejects values formerly admitted by the looser string-only validator.
- Stamps require lesson progress, all indexed exercises and a checkpoint with at least five items. They do not require a minimum number correct; this currently means checkpoint completion, consistent with the displayed completion wording. No new assessment threshold is inferred here.
