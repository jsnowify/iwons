## Original findings (historical; resolved as described above)

1. **P2 — Preview explanation fields accept focus but discard typing.** `src/components/learning-workspace.tsx:79,88` controls each textarea from persisted `learning.explanations`, then returns immediately from `onChange` when `preview` is true. After submitting the temporary repair/Parsons sample successfully, typing in “Explain to Tik” has no effect. It can even display an existing saved explanation in a preview. Use component-local preview explanation state, as LessonActivity already does. This blocks meaningful QA of the reflection interaction, although it does not write preview learning progress.

2. **P2 — A Parsons arrangement is lost on reload or track changes despite draft machinery.** `src/components/parsons.tsx:18-19` stores order only in React state. `src/components/learning-workspace.tsx:38-40` persists the unrelated `code` string for every exercise, including Parsons; it never persists the chosen block order. Reorder blocks, switch tracks, return: the arrangement resets. The short-session active phase survives, so resuming an exercise gives the appearance of a restored session while silently resetting this work. Persist a separate versioned per-exercise/per-track order through storage.ts and include it in backup validation, or explicitly describe that arrangements are temporary.

3. **P2 — Lesson Modify work and prediction are not restored in a saved short session.** `src/components/lesson-activity.tsx:21-24` holds guess/code only in component state; `src/components/ten-minute-session.tsx:34-36,58` saves only the outer session phase. Refreshing during the lesson step resets the prediction and edit while showing a saved-session continuation. LessonActivity's ordinary Modify draft also disappears on route/track changes. Restore drafts through storage.ts, with preview isolation, or clearly state the narrower resume guarantee. Exercise editor drafts already provide the expected pattern.

4. **P2 — A valid answer to the fill-in prompt is marked wrong.** `src/data/learning-demo.json:655,871` (same card in each track) asks “The program prints one ___.” `public/learn-data/tool-demo.json` supplies only `line`; `src/lib/foundations/lesson-engine.ts:46-49` performs exact matching with no accepted alternatives. “word” and “message” are true of this example but receive “Not yet.” Similarly the natural-language line-count question rejects “one.” Specify “Complete using the term for a row of output” or use explicit alternatives/choices. Keep exact matching for the actual output prediction, where capitalization matters.

5. **P2 — Parsons hints direct learners to repair a prefix they cannot edit.** `scripts/seed-learning-exercises-demo.mjs:15` generates the same three hints for both exercises; the resulting `src/data/learning-exercises-demo.json` has hints about comparing/changing the prefix. All Parsons blocks already contain `Desk: `, while the real task is dependency order. The hints do not progress toward arranging input/definitions before output and therefore leave a stuck beginner without the promised next step. Generate kind-specific hints: identify the use of `name`, locate where it is created, then place output after its dependencies; Java additionally needs its outer wrapper.

6. **P2 — Keyboard focus can disappear after moving a block to an edge.** `src/components/parsons.tsx:40-43` keeps focus on the activated Move up/down button, but that button becomes disabled when its block reaches the first/last position. Disabled controls leave the tab order and focus behavior varies by browser; the next action is not reliably apparent. Retain focus on the moved block or a remaining enabled move control and announce the new position. The native buttons provide a useful keyboard/touch alternative to drag, but this boundary case needs browser verification by the main reviewer.

## Optional improvements and guardrail observations

- **P3 — TypeScript silently adds a second idea.** `src/data/learning-demo.json:699,707` introduces `const message: string` and an identifier, but the line-2 annotation calls it a statement printing the “quoted message.” The quotes are on line 1. Explain that line 1 names the text and line 2 prints the stored value, or use the same direct output example as JavaScript. Java's wrapper is also unexplained, though its output annotation correctly points at line 3. The desk-label JS/TS samples use Node-style `require("fs")`, regex newline removal, and a type annotation; those are plausible runner idioms, but should be labeled supplied input plumbing rather than assumed first-year knowledge.
- **P3 — Feedback is mostly actionable, but not every item gives a next step.** Prediction, trace, failure, checkpoint explanations and recall misses name a concrete action. Successful RecallCard feedback (`src/components/recall-card.tsx:37`) hides `nextStep`; a learner receives a reason and rating controls, but no transfer action. Parsons success (“Each line runs in the order you chose,” line 32) explains execution in a way that adds little: ask the learner why output must follow the declarations. Runner-load catch messages also conflate loading, runtime, and custom JSON failures; diagnose these separately when evidence permits.
- **P3 — Preview Recall cannot retry a miss in place.** `src/components/recall-card.tsx:32-39` locks the response after checking and rating without a reset. DailyWarmup requeues misses, but the lesson preview tells learners to try again without providing that action. Offer a fresh-attempt button or a clear return path.
- **Readiness gates are useful structural/execution checks, not proof of teaching quality.** `scripts/validate-learning-content.ts:41-48` runs the example and Modify reference, and module validation requires hashed review evidence. However `src/lib/foundations/lesson-engine.ts:85-89` does not ensure a multiple-choice answer is among its options, and a nonempty `accepted`/reason/nextStep field is not a semantic check. Add membership validation and keep independent review for ambiguity and progressive hints. The minimum 250-word rule (`lesson-engine.ts:67`) can reward repetition in a one-operation sample. No sample should be marked ready merely because these checks pass.
- **Privacy/backup source findings:** the inspected public lesson/exercise objects do not contain their private solution/test packs; answer packs are fetched following interaction. They remain publicly downloadable by design, which is consistent with a static browser-only app. No initial-HTML leakage was found by source inspection, but no built HTML was inspected in this review. The exercise statement is supplied as server-renderable content. Storage access is centralized in storage.ts, version-6 envelopes include learning state and editor drafts, and imports validate that state. No new backend/database use was found. The draft omissions above are separate from the existing editor backup path.
- **Java availability:** the samples visibly disable checks without an endpoint and offer local execution instructions. LessonActivity/Parsons use `!settings.judgeUrl` while LearningWorkspace uses `!settings.judgeUrl.trim()`; normalize the check so a whitespace-only URL does not enable apparently available controls. No claim that an unconfigured Java browser runtime works was found.
- **Originality:** no obvious copied-source phrasing appeared in the samples. This is an editorial observation, not a provenance guarantee or external plagiarism search.

## Required learner-experience answers

**Would a first-year learner stay engaged?** The initial predict/run comparison, short edit, and optional break-and-repair task plausibly invite participation. Seven stages plus three recall cards and five checkpoint questions revisit one printed word/line; this sample could feel long after Modify. That is a design judgment about these temporary materials, not evidence about actual learners.

**Do interactions teach distinct things?** Predict tests a mental model; Run exposes the result; Modify connects an edit to changed output; the desk-label repair compares expected versus actual text; Parsons can teach data dependencies. The supplied trace and two line-count recall formats mostly repeat counting one execution. More controls do not by themselves create distinct learning tasks.

**Which screens feel passive/repetitive?** Make in preview explains future exercise links without an exercise; Recap summarizes the same facts; Investigate reveals its own one-line count before asking it. The checkpoint repeats original word, quote marks, line count, and changing quoted text. This is acceptable as control coverage but should not be treated as a model for a complete lesson's pacing.

**Does each feedback item give a next step?** No. Most miss/checkpoint feedback does, but success recall and generic Parsons success do not, and Parsons hints point at the wrong kind of action. Preserve the process-focused tone; fix those concrete gaps rather than adding praise or scores.
