## Initial findings (resolved on re-review)

1. **Medium � prediction is spoiled before the learner predicts.** `lessons/changing-a-value.json` story says that the register starts at eight and is replaced with nine; its idea explicitly says the third statement prints 9. `choosing-a-type.json` recap similarly supplies 3.5, and `converting-text.json` idea supplies 13. If the opening prediction follows the prose, the activity becomes answer copying. Keep the opening story to the setup and reveal the numerical conclusion after prediction/run, or confirm in browser that prediction precedes those passages. This is a presentation-dependent finding, not proof of current screen order.

2. **Medium � repeated checks do not all add a learning decision.** `names-and-values.json` prediction, trace question, second recall card, and `inspect-a-named-message.json` all reuse the unchanged Ready example. `changing-a-value.json` prediction, trace question, second recall card, and `trace-the-current-count.json` all ask for 9 from the identical sequence. After the first two checks, knowing the remembered answer can substitute for tracing. Change at least the external exercise or recall to a fresh value/order, or ask why the earlier value is not read. Keep a short direct retrieval check, but remove the extra identical decision.

3. **Medium � terminology and cross-track exposition burden the first lesson.** `names-and-values.json` introduces identifier, string, declaration, assignment, binding and output argument in quick succession; the JavaScript note also introduces `number` and reassignment before their lessons. The idea partially explains identifier and string through examples, but binding/declaration/argument lack a plain local definition. `constants.json` adds mutable objects and deeply immutable despite no objects being involved. Define only terms needed for the current action (for example, �initializer: the first value supplied�), remove unrelated JS numeric notes from this lesson, and shorten the object caveat to a later optional note. The concepts are accurate; the current vocabulary density weakens first-year clarity.

4. **Low � feedback calls a Python convention enforced.** `keys/exercise-choose-a-fixed-sign-edit.json`, every variant explanation, says �Python enforces only a convention here.� Python does not enforce that uppercase convention. Replace with �Python communicates this intent through a naming convention.� The lesson itself correctly explains the distinction.

5. **Low � worked-example feedback changes the stated task.** `keys/exercise-inspect-a-named-message.json` instructs �then change only the initializer,� while the public statement specifically requests running the unchanged example. `keys/exercise-inspect-a-text-conversion.json` similarly asks for a different string after an inspect/run task. Label these as optional follow-up exploration and give a concrete edit and expected check, or end with the task's requested compare/run action. An unqualified next step can confuse a learner returning to the exercise after feedback.

6. **Low � private reference for the fixed-sign edit shows the original sign.** `keys/exercise-choose-a-fixed-sign-edit.json` correctly selects option b, but all `referenceSolution` values still contain Open, whereas the statement requests the edit that prints Closed. Since this is a selection exercise, scoring by option is correct; however, any displayed reference solution would contradict the requested outcome. Store the edited initializer Closed or confirm this field cannot be shown for prediction tasks.

## Required reviewer answers

- **Would a learner stay engaged for the whole lesson?** The short programs and deliberate break/restore tasks provide useful agency, but not consistently for the full seven-minute estimate. The four long shared paragraphs and repeated unchanged checks can feel like explaining the same result again. Shorten prose and reserve repetition for a new example or a different reasoning task.
- **Do interactions teach distinct things?** Prediction versus running provides a useful expectation check; modification checks dependency; breaking quotes/order/reassignment tests boundaries. Tracing is distinct when it separates stored value from output expression (especially the 12 versus 13 example). It is much less distinct when every interaction asks for the same final 9.
- **Any passive or repetitive screens?** Both worked exercises supply complete runnable programs already shown in lessons. Their subgoal prompts are useful but can become passive unless the learner actually answers them before running. The identical Ready and 9 checks are the clearest repetition to revise. Browser behavior must establish whether these prompts require any meaningful interaction.
- **Does every feedback message give a next step?** Every authored lesson prediction/trace/recall key and checkpoint explanation reviewed contains a specific next action. Exercise explanations also contain actions and avoid ability praise. The exceptions are quality rather than absence: the worked-task next actions conflict with the unchanged-run instruction, and the fixed-sign wording misstates convention enforcement. Runtime/compiler framing is not contained in these files and was not assessed.
